# STIX v0.1.13

Released 2026-07-26.

## Security Contract

STIX proof tokens now bind the exact authorization request, caller-supplied raw-argument hash when available, stable action identifier, resource identifier, approval reference, and unique replay identifier. Approval tickets persist the same binding through the approvals service so a changed request cannot reuse an approval.

Target verification selects keys by JWT `kid`, checks the token algorithm against the configured key and allow-list, and requires resource matching and request/replay binding by default.

Enterprise enforcer mode forces `CLOSED` failure behavior. API keys must be mapped to workload identities, and actor ID, type, tenant, role, and attributes in the request must match that identity.

## Approval Flow

The SDK now retains the original request, polls the approval ticket, reauthorizes with `approval_ref`, and returns `ALLOW` only when the reauthorization returns a proof token. An approved ticket without a proof remains denied.

## Configuration

Enterprise deployments should configure:

```text
ENTERPRISE_MODE=true
API_KEYS=<comma-separated keys>
WORKLOAD_IDENTITIES={"<api-key>":{"actorId":"...","actorType":"SERVICE","tenant":"...","role":"..."}}
```

`WORKLOAD_IDENTITIES` is parsed at startup and API keys without a binding fail startup in enterprise mode.
